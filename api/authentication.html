API / Security boundary

Authentication

Every API request must prove who is calling, which tenant the caller belongs to, and which operation the caller may perform. PesaGuard uses bearer JWTs for service access; dashboard sessions and provisioned API keys are managed separately.

Contract status. The checked-in OpenAPI document defines bearerAuth with JWT semantics. API-key creation, rotation and revocation are credential-management procedures; use the deployment's control plane or operator workflow for those actions rather than assuming undocumented public endpoints.

Authentication overview

Authentication happens before tenant authorization, request validation, idempotency handling and business processing. A request that cannot be authenticated must not be treated as an anonymous request, and a valid identity must not be confused with permission to access every resource.

Identity

Proves the caller's credential is valid and has not expired or been revoked.

Context

Associates the request with the issuer, audience, tenant and environment in the credential.

Authorization

Checks scopes and roles before allowing the requested operation or resource.

API keys

An API key is a long-lived credential intended for a specific integration or service account. Treat the secret portion as equivalent to a password. The public identifier may be logged for identification, but the secret must never be written to source control, browser code, URLs or ordinary application logs.

API key types

TypeUseBoundary
Sandbox keyDevelopment and integration testingSandbox data and endpoints only.
Production keyLive transaction and reconciliation workloadsProduction tenant and production controls.
Service-account keyNon-human workload with a defined ownerOne workload, one owner, least-privilege scopes.
Test keyAutomated tests and failure scenariosShort lifetime, disposable data, no production access.

API key format

Use the key identifier to identify a credential and the secret to authenticate it. A typical provisioned key has a non-secret prefix and a high-entropy secret:

pg_sbx_01J... . secret-value-returned-once

The exact prefix and header name are deployment configuration. Never infer environment or tenant access from a prefix alone; validate the credential with the server.

Creating, viewing, rotating and revoking keys

  1. Create a key for one integration, record its owner, environment, scopes and expiry, and display the secret only once.
  2. View metadata such as key id, owner, created time, last-used time, expiry and status. The secret must not be recoverable.
  3. Rotate by creating the replacement first, deploying it, observing successful traffic, then revoking the old key. Keep overlap short and controlled.
  4. Revoke immediately when a key is exposed, unused, mis-scoped or owned by a departing service. Revocation must be followed by a failed-authentication check.

API key expiration, permissions and scopes

Give every key an expiry that matches the workload. A key should carry only the scopes it needs, such as dashboard:read, transactions:read, transactions:write, reconciliation:read or reconciliation:write. Separate read and write credentials when practical. A valid key with an insufficient scope must receive 403, not a misleading 401.

Bearer authentication

The OpenAPI contract declares HTTP bearer authentication with bearerFormat: JWT. Send the access token on every protected request. Do not send it as a query parameter or in a custom header unless the deployment explicitly documents that compatibility behavior.

Access tokens and token format

Access tokens are short-lived credentials containing claims such as issuer, audience, subject, tenant and expiry. Clients must treat the token as opaque: do not depend on decoding it to make authorization decisions, and do not accept a token merely because its payload can be parsed.

Obtaining, refreshing and revoking a token

Obtain an access token through the authenticated login or identity-provider flow assigned to your deployment. Keep refresh tokens in a protected server-side store. Refresh before access-token expiry, rotate refresh tokens when the identity provider requires it, and discard the token set on logout, suspected compromise or refresh-token reuse.

Organization and tenant identification

Tenant identity comes from the authenticated principal and server-side membership, not from an arbitrary client-supplied tenant id. If a route accepts an organization selector, the server must verify that the caller belongs to it. Never place tenant ids in a credential chosen by the client without checking membership.

Environment-specific credentials

Never promote a sandbox key to production or copy production secrets into a local .env file that may be committed. Environment migration requires issuing a new credential in the destination environment and validating access before cutover.

JavaScript

const response = await fetch(`${process.env.PESAGUARD_API_URL}/api/v1/tenant/current`, {
  headers: {
    Authorization: `Bearer ${process.env.PESAGUARD_ACCESS_TOKEN}`,
    Accept: "application/json"
  }
});

if (!response.ok) throw new Error(`PesaGuard request failed: ${response.status}`);

Security best practices

  • Never expose secret keys. Keep them out of browser bundles, mobile logs, screenshots, tickets, URLs and source control.
  • Use server-side key storage. Store credentials in an approved secret manager and inject them at runtime.
  • Use environment variables carefully. Restrict process visibility, validate required values at startup and do not print the environment.
  • Rotate deliberately. Use overlapping credentials only for the measured deployment window, then revoke the old one.
  • Use least privilege. Separate read, write, operator and migration roles; review scopes regularly.
  • Require HTTPS. Reject plaintext API URLs outside local development and validate certificates.
  • Use IP restrictions where appropriate. Treat allowlists as defense in depth, not as a replacement for credentials.
  • Sign sensitive requests. For integrations that require proof of payload integrity, use the deployment's documented request-signing contract.

Webhook authentication

Webhook authentication is sender verification, not API-request authentication. Verify the signature against the raw request body before parsing or acting on it, enforce a timestamp window, reject mismatches, and record the delivery id for idempotent processing.

See webhook signature verification for the receiver procedure. API credentials must never be embedded in outbound webhook payloads.

Idempotency authentication considerations

Authentication and idempotency solve different problems. Authenticate every retry, bind the idempotency key to the authenticated tenant and operation, and reject reuse with a different request body. Never let an idempotency key bypass permission checks.

Authentication flow

  1. Login / credential flow: the identity provider or control plane verifies the user or service secret and issues a scoped credential.
  2. API request flow: the client sends the credential over HTTPS with the request.
  3. Token validation flow: middleware validates signature, issuer, audience, expiry, revocation state and tenant membership.
  4. Authorization: route policy checks role and scope before loading tenant data or mutating state.
  5. Audit: the service records authentication success, failure, revocation and sensitive credential events without recording secrets.

Multi-tenant authentication

Organization access

A principal may belong to one or more organizations, but each request executes in one authorized tenant context. Verify membership on every context switch and apply the same tenant boundary to reads, writes, exports, cache keys, events and replays.

User vs API authentication

User credentials represent a person and should support interactive lifecycle controls. API credentials represent a workload and must have an owner, purpose, expiry and rotation plan. Do not share a personal user token with a background service.

Service accounts and credentials

Use a dedicated service account per integration or bounded workload. Document its owner, scopes, environment, source IPs, expiry and emergency contact. Disable the account before deleting its records so failures are observable during the transition.

Permissions and roles

Roles group permissions for administration; scopes express the access granted to a credential. A role or scope must never grant access outside the principal's tenant membership.

Authentication middleware

Authentication middleware should run before route handlers and expose a normalized principal to them. It should fail closed, avoid leaking whether a user or tenant exists, attach a correlation id, and keep credential material out of request logs. Authorization belongs in policy checks close to the operation, not only in the global middleware.

Authentication failure handling

Return the standard error envelope, use 401 for missing or invalid authentication and 403 for an authenticated principal that lacks permission. Apply bounded backoff to repeated failures and alert on unusual failure patterns without locking out legitimate recovery paths.

Common authentication mistakes

  • Using Bearer with an API key or sending a JWT in a query string.
  • Using a sandbox credential against production or the reverse.
  • Logging full authorization headers during debugging.
  • Retrying a rejected credential indefinitely instead of renewing or escalating.
  • Trusting a client-supplied tenant id without membership validation.

Credential lifecycle

Credential rotation procedure

  1. Inventory the credential and confirm its owner, scope and environment.
  2. Issue and securely distribute the replacement.
  3. Deploy and verify authenticated reads and writes.
  4. Monitor old-key traffic, then revoke the old credential.
  5. Record the change and close the rotation evidence.

Credential compromise procedure

  1. Revoke the exposed credential immediately.
  2. Preserve authentication and request audit events.
  3. Identify affected tenants, scopes, time window and source addresses.
  4. Issue a replacement and validate dependent services.
  5. Review data access, rotate related secrets and document the incident.

Sandbox to production authentication

Provision production credentials separately, review scopes and tenant membership, deploy through the production secret path, perform a harmless authenticated health or read check, and only then enable writes. Never copy sandbox data or secrets into production.

Authentication audit logs

Security events

Audit authentication success and failure, credential creation, rotation, revocation, scope changes, tenant membership changes, account lockout and suspicious source changes. Record actor, credential id, tenant, environment, timestamp, outcome and request id; never record passwords, raw tokens or secret key values.

Authentication changelog

Review the deployment's release notes and OpenAPI document when authentication behavior changes. A change to issuer, audience, signing keys, scopes, token lifetime, headers or error semantics requires an integration review and a staged migration.

Authentication FAQ

Should a browser call the API with a service key?

No. Keep service credentials server-side and expose only the minimum application session behavior to the browser.

Can I decode a JWT to decide access?

No. The server must validate the signature and claims, then apply authorization policy.

What should I do with a 401?

Check environment and header formatting, renew or replace the credential once, and preserve the request id if the failure remains.
