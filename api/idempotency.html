Idempotency

A retried write must produce one durable outcome for one logical operation. Idempotency keys protect writes such as sending a communication when networks fail after the server has accepted a request.

Client contract

Generate a unique key for each logical operation and reuse it for retries of that operation only. Bind the key to the authenticated tenant, route and request body. Never generate a new key for every transport retry or reuse a successful key for a different operation.

POST/api/v1/communications/sms
POST /api/v1/communications/sms
Authorization: Bearer <token>
Idempotency-Key: sms-8f9c...
Content-Type: application/json

{
  "recipient": "+254700000000",
  "message": "Your payment was received."
}

Where idempotency keys apply today

RouteKey inputMissing keyRepeated key
POST /api/v1/communications/smsIdempotency-Key header or idempotency_key body field400 INVALID_REQUESTReturns the existing notification (id, status, tenant_id) with 202; nothing new is queued.
POST /api/v1/communications/emailSame as SMS400 INVALID_REQUESTSame request and response shape.

A key is unique per tenant, so two tenants can use the same value. No other route in the canonical backend app reads an idempotency key, and the transaction endpoints are read-only.

Outcome matrix

SituationExpected behavior
First request acceptedProcess once and persist the outcome associated with the key.
Retry with same bodyReturns the original notification with 202.
Same key, different bodyNot detected today: the original notification is returned and the new body is ignored, so do not rely on a 409. Planned Conflict detection.
Unknown result after timeoutRetry with the same key, then reconcile by resource id or provider reference.
Expired keyCommunication keys do not expire in the current code; a reused key returns the original notification. For other writes, do not assume the operation is absent; consult the resource or reconciliation record.

Retries and replay

Use exponential backoff with jitter for network failures and 5xx responses. A 409, if a route ever returns one, is not permission to create a second record. Replays from a dead-letter queue must preserve the original event identity, tenant and idempotency key, and every replay should be auditable.
