Idempotency

A retried write must produce one durable outcome for one logical operation. Idempotency protects transaction creation, provider callbacks, webhook handling and operator actions when networks fail after the server has accepted a request.

Client contract

Generate a unique key for each logical operation and reuse it for retries of that operation only. Bind the key to the authenticated tenant, route and request body. Never generate a new key for every transport retry or reuse a successful key for a different transaction.

POST /api/v1/transactions
Authorization: Bearer <token>
Idempotency-Key: transaction-create-8f9c...
Content-Type: application/json

Outcome matrix

SituationExpected behavior
First request acceptedProcess once and persist the outcome associated with the key.
Retry with same bodyReturn the original outcome or a documented in-progress response.
Same key, different bodyReject as a conflict; do not mutate the original operation.
Unknown result after timeoutRetry with the same key, then reconcile by resource id or provider reference.
Expired keyDo not assume the operation is absent; consult the resource or reconciliation record.

Retries and replay

Use exponential backoff with jitter for network failures and 5xx responses. A 409 is not permission to create a second record. Replays from a dead-letter queue must preserve the original event identity, tenant and idempotency key, and every replay should be auditable.
