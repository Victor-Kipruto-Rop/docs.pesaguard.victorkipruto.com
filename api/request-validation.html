Request validation

Requests are validated before they can affect provider state, reconciliation or audit records. Validation rejects malformed, ambiguous and unsafe data instead of silently coercing it into a plausible financial event.

Validation layers

LayerExamplesFailure response
TransportMethod, content type, body size and JSON syntax.400
SchemaRequired fields, types, formats and enum values.400 or 422
DomainCurrency, amount, timestamps, references and state transitions.422
AuthorizationTenant ownership and permitted operation.401 or 403
ConflictDuplicate reference or idempotency mismatch.409

Example validation response

{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Request validation failed.",
    "request_id": "request_01J...",
    "details": [
      {"field": "amount", "reason": "must be greater than zero"},
      {"field": "currency", "reason": "must be an ISO 4217 code"}
    ]
  }
}

Client checklist

  1. Validate locally for fast feedback, but treat the server as authoritative.
  2. Send decimal amounts using the documented representation; never rely on binary floating-point formatting.
  3. Use UTC timestamps and stable provider references.
  4. Do not retry unchanged invalid input.
  5. Preserve the request id when escalating a rejected payload.

Data-quality boundary

Validation runs before matching and reconciliation. Invalid records must remain visible as failures with field-level reasons; they must not be silently dropped, rounded, defaulted or marked successful.
