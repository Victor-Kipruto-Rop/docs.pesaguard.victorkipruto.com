Sorting

Sorting makes collection reads reproducible. Use only fields and directions documented for the endpoint, and always pair an order with pagination when scanning or exporting data.

Ordering rules

RuleReason
Unspecified order is unstableInsertion order can change after writes, retries, indexing or reconciliation.
Use a deterministic tie-breakerEqual timestamps or amounts need a unique id to prevent page drift.
Sort before paginatingChanging order between pages can duplicate or skip records.
Keep filters and sort fixedAn export is reproducible only when its full query remains unchanged.

Example

GET /api/v1/discrepancies?status=open&sort=created_at:asc,id:asc&page=1&limit=50

If an endpoint does not publish a sort parameter, do not invent one. Use the endpoint's documented default and ask for a contract update when a stable export order is required.

Reconciliation scans

For long-running scans, use a bounded time window and record the final cursor or last-seen unique id. Re-run overlapping windows when necessary, then deduplicate by the server resource id rather than assuming page boundaries are immutable.
