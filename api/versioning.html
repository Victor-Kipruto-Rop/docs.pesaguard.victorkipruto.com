Versioning

Versioning gives integrations time to migrate without silently changing financial or reconciliation semantics. Public routes use a versioned namespace where documented; compatibility aliases must be treated as transitional.

Compatibility policy

  • A version remains supported for at least 90 days after a deprecation notice is published.
  • Breaking changes require a new versioned route prefix, never a silent shape change in place.
  • Deprecations are announced in release notes and in the OpenAPI specification.
  • Additive fields can still affect strict deserializers, so clients should tolerate unknown response properties.

Migration procedure

  1. Compare the old and new OpenAPI documents.
  2. Classify route, schema, validation, error and authorization changes.
  3. Add compatibility tests against both versions.
  4. Deploy the new client behind a measured rollout.
  5. Monitor errors, latency, reconciliation outcomes and old-version traffic.
  6. Remove the old version only after its consumers have migrated and the support window closes.

Versioned request

GET /api/v1/tenant/current
Authorization: Bearer <token>
Accept: application/json

Do not infer a version from a server error or guess a compatibility alias. Read the deployment's OpenAPI document and release notes, then pin the route version in configuration.
