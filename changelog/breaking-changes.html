Breaking changes

Breaking changes alter a request, response, authorization rule or operational guarantee in a way that can make an existing integration fail or produce a different result.

Migration rule. Do not infer compatibility from a successful HTTP response alone. Compare the OpenAPI contract, validation behavior, error semantics and reconciliation outcomes before promoting a client change.

What counts as breaking

AreaBreaking exampleMigration check
RoutesRemoving a path, method or documented compatibility alias.Search all client calls and generated SDK methods.
AuthenticationChanging issuer, audience, scopes, headers or token lifetime.Test credential issuance, renewal and tenant access.
RequestsMaking an optional field required or rejecting an accepted value.Run validation cases for every environment.
ResponsesRemoving fields, changing types or altering pagination metadata.Use tolerant deserialization and contract fixtures.
ErrorsChanging status codes or retry meaning.Review retry, idempotency and alerting logic.
Data behaviorChanging tenant scope, ordering, matching or reconciliation semantics.Run a controlled comparison on representative data.

Notice and support policy

  1. Publish the change with affected versions and migration notes.
  2. Keep the previous version supported for at least 90 days after notice.
  3. Expose the new contract and any deprecation signal in the running deployment.
  4. Monitor old-version traffic and integration failures during migration.
  5. Remove the old behavior only after the support window and consumer review.

Client migration checklist

  • Pin the API version in configuration.
  • Compare OpenAPI documents in CI.
  • Test authentication, tenant boundaries, validation, errors, retries and pagination.
  • Deploy behind a measured rollout with rollback prepared.
  • Record the migration owner, date and evidence.

Migration test plan

Test areaMinimum evidence
AuthenticationSuccessful request, expired token, revoked credential and insufficient scope.
ReadsFiltering, sorting, pagination and empty-result behavior remain understood.
WritesValidation failures, idempotent retry and conflict handling are tested.
Tenant safetyCross-tenant identifiers cannot return or mutate another tenant's data.
OperationsRequest ids, latency, error rates and reconciliation outcomes are observable.

Rollout and rollback

Start with a low-volume tenant or internal integration. Compare success rate, 4xx and 5xx responses, latency, queue pressure and reconciliation results against the previous version. Keep the old client or route available until the new path is proven. If rollback is required, stop new writes first, preserve idempotency keys, reconcile in-flight operations and then restore the previous client version.

Deprecation communication

A deprecation notice should name the old and replacement routes, affected scopes, behavior differences, first notice date, removal date, test environment availability and support contact. Do not communicate a removal date without confirming consumer traffic and a rollback plan.
