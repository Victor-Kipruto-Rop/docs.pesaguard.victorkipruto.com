Concepts

Architecture

PesaGuard separates synchronous acceptance from asynchronous processing so provider events can be acknowledged durably, retried safely and reconciled with evidence. Flask and SQLAlchemy expose the API, PostgreSQL owns durable state, Redis and RQ run bounded work, Kafka transports events, and Alembic manages schema change.

ComponentRole
Flask + SQLAlchemy APIOperational and dashboard endpoints; publishes its own OpenAPI document.
PostgreSQLProduction store. Tenant predicates are enforced here, not in application code.
Redis + RQAsynchronous work and bounded retries.
KafkaEvent transport between ingestion, reconciliation and notification stages.
AlembicSchema migrations with deliberate compatibility paths.

Event path

  1. Ingress: authenticate the API caller or verify the provider signature.
  2. Validation: normalize the payload and reject malformed or ambiguous data.
  3. Durability: write the event, idempotency key and audit record within the transaction boundary.
  4. Dispatch: publish an outbox event and let workers process it asynchronously.
  5. Reconciliation: match the provider event to the internal record and persist the result.
  6. Observation: expose state, metrics, alerts and audit evidence to operators.

Failure boundaries

FailureExpected protection
Process crash after receiptDurable event and idempotency record allow safe replay.
Queue or broker outageAccepted work remains visible and is retried or dead-lettered.
Database failureRequests do not claim success before required state commits.
Consumer failureDelivery retries preserve event identity and tenant context.
  • Durability first: work is acknowledged only after the required durable state or idempotency record is written.
  • Safe failure: transient failures retry with bounded backoff; exhausted work is dead-lettered, never discarded.
  • Evidence by default: correlation IDs, structured logs, metrics and append-only audit events explain what happened.

Design principles

  • Tenants
  • Idempotency
  • Environments

The architecture is intentionally boring at its boundaries: durable state first, explicit retries, tenant predicates close to data, and audit evidence for decisions. Those constraints make high-volume financial behavior measurable rather than optimistic.
