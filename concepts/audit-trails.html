Audit trails

An audit trail is the durable explanation for a system decision. Every match, exception, review, credential event and configuration change records its actor, tenant, reason and correlation context. Entries are added, never rewritten.

  • Decisions keep their reason: accept, reject or escalate is stored with the actor and the transaction context.
  • History survives turnover: institutional knowledge stays queryable when the team changes.
  • Secrets are excluded: tokens, keys and credentials never enter audit entries; sensitive fields are redacted at logging boundaries.

Audit event anatomy

FieldWhy it matters
Event typeIdentifies the action or decision.
ActorNames the user, service account or worker responsible.
TenantConstrains the event to the organization it belongs to.
Resource and event idsConnects the decision to the transaction, provider event or request.
Reason and outcomeExplains what was decided and why.
TimestampSupports ordering, investigation and retention policy.

What belongs in the trail

  • Authentication successes, failures, credential creation, rotation and revocation.
  • Tenant membership and permission changes.
  • Provider callbacks, matching outcomes, exceptions and reviewer decisions.
  • Configuration changes affecting thresholds, routes, providers or notifications.
  • Replay, export and administrative actions.

Audit integrity and privacy

Append-only does not mean unrestricted. Enforce tenant-scoped access, protect retention storage, redact secrets and minimize sensitive payload copies. Operators should be able to correlate an audit event with logs and metrics without exposing passwords, raw tokens, API secrets or unnecessary personal data.

Investigation workflow

  1. Start with the request, transaction or provider event id.
  2. Load the tenant-scoped audit timeline.
  3. Compare state transitions with worker and API logs.
  4. Confirm the actor, reason and downstream notification outcome.
  5. Record the investigation conclusion without rewriting original evidence.

An audit-ready trail needs three properties more than it needs volume: entries can only be added, each entry identifies who did what, and each entry traces back to the transaction that caused it.
