Concepts

Idempotency Live

Retries are expected in payment systems — from Daraja, from your consumers, from operators. Idempotency is enforced where writes happen, so a repeated operation is safe by construction.

<<<<<<< HEAD
  • Enforced at the write — a duplicate event is rejected by the database, not by an application check that can be forgotten.
  • Events persist before processing — so a crash between receipt and processing leaves a record, not a gap.
  • Replay-safe operations — dead-letter replay, manual reprocessing and provider retries all run under the same rule.
  • Acknowledge only what persisted — a success response never claims durable processing that did not happen.

The invariant in one line: the same logical event, delivered twice, produces one financial record and one audit entry.
