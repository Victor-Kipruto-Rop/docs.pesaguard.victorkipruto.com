Idempotency

Retries are expected in payment systems: providers redeliver callbacks, clients retry timeouts and operators replay failed work. Idempotency binds those attempts to one logical operation so a duplicate cannot become a second financial record.

  • Enforced at the write: a duplicate event is rejected by the database, not by an application check that can be forgotten.
  • Events persist before processing: so a crash between receipt and processing leaves a record, not a gap.
  • Replay-safe operations: dead-letter replay, manual reprocessing and provider retries all run under the same rule.
  • Acknowledge only what persisted: a success response never claims durable processing that did not happen.

Identity of an operation

An idempotency key is meaningful only with its tenant, operation, authenticated principal and request payload. The same key with a different body is a conflict, not a new request. A new logical transaction requires a new key.

Failure timeline

  1. The client sends a request with a unique key.
  2. The service stores the key and durable outcome before acknowledging success.
  3. A network timeout leaves the client uncertain.
  4. The client retries with the same key.
  5. The service returns or resumes the original outcome instead of creating another record.

What idempotency does not solve

It does not authorize a caller, validate a payload, guarantee provider settlement or resolve a reconciliation mismatch. Those checks still run on every attempt before the stored outcome is returned.

The invariant in one line: the same logical event, delivered twice, produces one financial record and one audit entry.
