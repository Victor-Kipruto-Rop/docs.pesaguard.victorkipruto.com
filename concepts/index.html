Concepts

These concepts explain how PesaGuard turns provider events into tenant-scoped, auditable reconciliation outcomes. Read them as one system: architecture establishes the flow, lifecycle names what is known, and the safety concepts prevent silent corruption.

ConceptIn one line
ArchitectureIngest, validate, reconcile, analyze, alert, resolve, report.
ReconciliationDeterministic matching with exceptions instead of silence.
Transaction lifecycleThe states a payment moves through, and what each means.
IdempotencyA retry never becomes a second financial record.
TenantsDatabase-enforced boundaries, measured with zero leakage.
AnomaliesNamed signals to review: never automatic verdicts.
Audit trailsAppend-only evidence for every decision.

Recommended reading path

  1. Architecture to understand the components and durable boundaries.
  2. Transaction lifecycle to learn what each payment state proves.
  3. Reconciliation to see how provider and internal records become a result.
  4. Idempotency and Tenants to understand safe retries and isolation.
  5. Anomalies, Fraud detection and Audit trails to follow review and evidence.

Reference workflow

Every capability follows the same boundary sequence: authenticate the caller or verify the provider signature, resolve tenant identity, validate and normalize, enforce idempotency, persist the durable record and audit event in one transaction, publish through the outbox, then reconcile, notify, measure and expose a traceable result.

Input

Provider callbacks and API requests are authenticated, validated and normalized before they are trusted.

Decision

Matching, anomaly signals and human review produce explicit states and reasons rather than hidden guesses.

Evidence

Tenant context, event identity, request ids and audit records make outcomes explainable later.
