Concepts

Tenants

A tenant is the security and data boundary for one organization. Every query, mutation, export, cache key, event and audit record carries an authorized tenant scope, with database enforcement protecting against application omissions.

  • Tenant predicates are part of the data access: a query without an authorized tenant resolves to nothing, not to everything.
  • IDs are not globally trusted: detail lookups must include tenant and account predicates.
  • Measured, not assumed: the committed load test exercised 100 tenants concurrently and recorded zero cross-tenant rows.

Tenant context flow

  1. Authenticate the user or service identity.
  2. Resolve its organization membership and permitted roles.
  3. Attach one tenant context to the request or worker message.
  4. Apply the context to reads, writes, exports, cache keys and events.
  5. Record the tenant with audit and operational evidence.

Isolation checklist

SurfaceRequired control
DatabaseTenant predicates or row-level policy are applied to every access path.
Background workJobs carry tenant context and cannot fall back to a global query.
CacheKeys include tenant scope and invalidation respects that boundary.
ExportsExport jobs and files are authorized for one tenant.
EventsPublished messages retain tenant identity through retries and replay.

Testing tenant safety

Run concurrent tests with multiple tenants, identical resource ids and overlapping filters. Verify that reads return zero rows across boundaries, writes cannot target another tenant, and logs and exports do not disclose identifiers from unrelated organizations.

The reason this lives in the database rather than the application: handlers change constantly, and one missed check is enough to leak data. A boundary that only protects reads is not a boundary: isolation covers writes, exports, cache keys, events and replays too.
