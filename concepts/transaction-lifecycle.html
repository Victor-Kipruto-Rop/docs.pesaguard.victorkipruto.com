Concepts

Transaction lifecycle

A transaction state is a statement about evidence, not a decorative label. Each transition has a precondition, an actor or worker, and an audit event so an operator can explain why the payment is in its current state.

StateMeaning
ReceivedA callback arrived and passed validation; duplicates were rejected on write.
MatchedA deterministic pairing exists against an internal record, with evidence retained.
UnmatchedNo internal candidate was found; the payment queues with the reason.
ExceptionA difference exists (amount, reference or tolerance) and awaits review.
ResolvedA reviewer decided with a written reason; the decision is in the audit trail.

Transition rules

FromToRequired evidence
ReceivedMatchedDeterministic candidate satisfies configured matching rules.
ReceivedUnmatchedSearch completed without a valid candidate.
MatchedExceptionLater evidence exposes an amount, reference or state conflict.
ExceptionResolvedAuthorized reviewer records a decision and reason.

Reading a transaction state

Consumers should treat state as a durable workflow signal and use the transaction, provider event, reconciliation result and audit trail together. A state change is not proof that money moved unless the state definition and provider evidence say so.

Operational handling

  • Poll or subscribe using the documented API and webhook behavior rather than repeatedly creating work.
  • Do not skip exception review by writing a final state directly.
  • Use idempotency when retrying a state-changing operation.
  • Preserve the original event and reviewer reason when correcting a mistake.
