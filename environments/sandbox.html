Environments

Sandbox

PesaGuard does not provide a mocked sandbox in this deployment model. Staging is the test environment: it runs real services and reconciliation behavior with isolated data stores and credentials.

Sandbox translation

Use staging as the safe testing boundary, not a fictional endpoint that behaves differently from production.

REAL SERVICESISOLATED DATA

Safe to test

Authentication failures, duplicate delivery, malformed payloads, retries, reconciliation exceptions and webhook verification.

Never copy

Production credentials, personal data, production broker topics, signing keys or unreviewed provider connections.

What “sandbox” means here

Use the word sandbox for a safe testing objective, not for a separate fake runtime. A staging deployment can exercise real authentication, queues, provider adapters, retries and reconciliation without granting access to production data.

Safe test data

  • Use synthetic identities, references and amounts.
  • Do not paste production credentials or personal data into test requests.
  • Mark test transactions so reviewers can distinguish them from operational work.
  • Clean up test providers, keys and queued work after a test campaign.

Recommended test sequence

  1. Confirm the URL is staging and the credential is staging-only.
  2. Run an authenticated read check.
  3. Test valid, invalid, duplicate and delayed events.
  4. Verify matching, exception, retry and audit outcomes.
  5. Capture request ids and evidence for the production review.

Boundaries

Staging may share code and deployment patterns with production, but it must not share databases, broker topics, secrets or tenant data. See staging for the concrete topology and testing guidance for scenarios.
