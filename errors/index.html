Errors

Errors and error codes

PesaGuard errors are designed to help a client decide what to fix, what to retry and what to escalate. Every failure carries a stable code, a human-readable message and a request id for operator correlation.

Failure handling model

Classify the status, preserve the request id, apply the documented recovery rule, and never retry a write without idempotency protection.

Full reference: API · Errors: envelope, status classes and client behaviour from 400 through 504.

  • Stable codes are part of the public contract; message copy is not.
  • 409 conflicts usually mean a duplicate under idempotency: re-read rather than re-send.
  • Quote the request id in support conversations; it is the correlation key operators search for.

Status family guide

FamilyMeaningDefault client action
400 / 422Request cannot be accepted.Correct input; do not retry unchanged.
401 / 403Identity or permission problem.Renew credentials or correct scope and tenant context.
404 / 409Resource or state conflict.Re-read within tenant scope and reconcile state.
429Capacity or abuse limit.Back off, reduce concurrency and honor retry guidance.
5xxService or gateway failure.Bounded retry with correlation and escalation.

Client error-handling sequence

  1. Capture status, code, request id and safe request context.
  2. Redact authorization headers, secrets and sensitive payloads.
  3. Apply the status-specific action below.
  4. Use the same idempotency key for an uncertain write retry.
  5. Escalate repeated failures with timestamps, environment and request ids.
