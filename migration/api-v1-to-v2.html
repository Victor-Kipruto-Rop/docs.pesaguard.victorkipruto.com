Migration

API v1 to v2

A developer runbook for a future route-version migration. It explains how to compare contracts, introduce compatibility, test tenant-safe behavior and retire v1 without duplicating financial work.

Current contract boundary

The documented public route remains /api/v1. The OpenAPI document version 2.0.0 describes the specification; it does not create an /api/v2 route.

COMPAREDUAL-RUNRETIRE
No v2 migration announced

Do not change a client from /api/v1 to /api/v2 until the deployment publishes the route, OpenAPI contract, compatibility window and migration owner. Treat a guessed v2 URL as an integration defect.

What changes in a route migration

A route version is a compatibility boundary for client-visible behavior. Compare more than paths: authentication, tenant context, validation, response shape, error semantics, ordering, pagination, rate limits, idempotency and reconciliation meaning can all break a client even when the HTTP method stays the same.

Before coding

  1. Identify every caller, SDK, background worker, export job and webhook consumer using v1.
  2. Record the environment, tenant, credential scopes and traffic volume for each caller.
  3. Fetch the running v1 contract and preserve it as a versioned build artifact.
  4. Obtain the announced v2 contract from the same deployment or staging target.
  5. Generate a machine-readable diff, then review behavioral changes manually.
  6. Assign an owner for client rollout, support, rollback and v1 retirement.

Contract comparison commands

Compare contracts from the environment being migrated. Do not compare a local static document with a production route and assume they describe the same deployment.

curl --fail "$PESAGUARD_API_URL/api/v1/openapi.json" -o openapi-v1.json
curl --fail "$PESAGUARD_API_URL/api/v2/openapi.json" -o openapi-v2.json
node ./scripts/compare-openapi.js openapi-v1.json openapi-v2.json

The comparison command is illustrative until a v2 contract and diff tool are published. The important control is to store both inputs and review the resulting route, schema, security and response changes in version control.

Compatibility patterns

Client-side version switch

Keep v1 and v2 adapters behind one application interface. Select the adapter through deployment configuration, not scattered path strings, so rollback changes one controlled value.

const api = process.env.PESAGUARD_API_VERSION === "v2"
  ? createV2Client(config)
  : createV1Client(config);

return api.retrieveTransaction(transactionId);

Read compatibility

When response fields differ, normalize both versions into one internal model and preserve the source version for debugging. Do not silently map a missing financial field to zero or an unknown status to success.

Write compatibility

Send writes to one version at a time unless the migration contract explicitly requires dual-write. If dual-write is required, use separate idempotency namespaces, reconcile both outcomes and define which version is authoritative.

Staging test plan

ScenarioEvidence required
AuthenticationValid token, expired token, revoked credential and insufficient scope.
Tenant isolationSame resource id across two tenants cannot cross-read or cross-write.
ValidationRequired fields, enum boundaries, amount and timestamp failures match the new contract.
RetriesTimeout and 5xx retry with the same key produces one durable outcome.
PaginationStable sort, complete iteration and changing-collection behavior are understood.
ReconciliationMatched, unmatched, exception and resolved outcomes retain equivalent evidence.
Operational loadRate limits, latency, queue lag, error rates and request ids are observable.

Rollout sequence

  1. Deploy the v2-capable client without enabling v2 traffic.
  2. Run contract and integration tests against staging.
  3. Enable v2 for an internal or low-volume tenant.
  4. Compare status, latency, error codes, duplicate rates and reconciliation outcomes with v1.
  5. Increase traffic in measured stages while monitoring v1 usage.
  6. Publish the deprecation notice and keep v1 supported for at least 90 days.
  7. Retire v1 only after consumer traffic reaches zero and the support owner approves.

Rollback decision

Rollback if authentication failures, authorization denials, validation rejects, duplicate writes, reconciliation differences or unexplained latency exceed the agreed threshold. Switch new traffic back to the v1 adapter, preserve v2 request and event ids, and reconcile any in-flight writes before declaring the rollback complete.

Developer migration checklist

  • Version routes in configuration, not in copied snippets.
  • Keep unknown response fields non-fatal.
  • Match on stable error codes, never message prose.
  • Preserve idempotency keys across retries and migration adapters.
  • Record the API version with request, transaction and audit telemetry.
  • Delete compatibility code only after the published sunset date and traffic review.
