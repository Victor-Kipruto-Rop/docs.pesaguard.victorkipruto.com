Migration

Migrations

Migration guidance for changes that can affect stored data, API clients, webhook consumers or deployment topology. Treat migration as a controlled operation with evidence, compatibility checks and a rollback decision.

Change without losing context

Separate schema, API and consumer changes, then move them through staging before production.

COMPAREVERIFYROLL BACK
  • Schema: Alembic revisions, safe backfills, no production schema creation outside migrations.
  • API: breaking changes require a new versioned prefix; the previous version stays supported for at least 90 days after notice.
  • Deprecations: announced in release notes and the OpenAPI document.

TrackUse whenGuide

Universal migration sequence

  1. Identify affected tenants, clients, workers and consumers.
  2. Compare the old and new contract or schema.
  3. Make the change additive and backward-compatible where possible.
  4. Test data, authorization, retries, idempotency and reconciliation outcomes in staging.
  5. Roll out gradually with metrics and rollback ready.
  6. Remove compatibility behavior only after the support window and traffic review.

Change classification

ClassExampleRequired control
AdditiveNew optional response field or new event type.Tolerant consumers and contract tests.
BehavioralSame route, but changed defaults, ordering or validation.Representative data comparison and operator review.
BreakingRemoved field, route, scope or accepted request format.New version, notice and supported migration window.
Data migrationBackfill, index or persistent shape change.Backup, reversible migration and capacity test.

Go / no-go review

  • Go only when the affected consumer inventory is complete.
  • Go only when staging tests cover success, failure, retry and replay.
  • Go only when dashboards show errors, latency, queue lag and reconciliation outcomes.
  • No-go when rollback would lose event identity, duplicate a write or hide an exception.

Migration evidence

Retain the contract versions, test results, owner, approval, deployment timestamp, request ids and rollback decision. A successful deployment is not proof that consumers have migrated.
