Migration

Webhook migrations

Webhook consumers must be able to tolerate retries, additive payload fields, signature rotation and controlled event changes. Prepare the receiver before changing the producer.

Upgrade the receiver first

Verify raw-body signature handling, idempotency and unknown-field tolerance before enabling a new webhook contract.

VERIFYDUAL-RUNOBSERVE

Webhook migration sequence

  1. Read release notes and compare event catalog or payload schema.
  2. Make the consumer tolerant of additive fields and unknown event types.
  3. Deploy signature verification and secret rotation support.
  4. Preserve delivery id, event id and tenant context for idempotent handling.
  5. Test retries, out-of-order delivery, malformed payloads and duplicate events.
  6. Enable the producer change and monitor delivery, rejection and dead-letter rates.

Compatibility checklist

SurfaceConsumer requirement
SignatureVerify the raw request body before parsing and support the announced secret overlap.
PayloadIgnore unknown fields, validate required fields and preserve the original body for audit.
DeliveryReturn acknowledgement only after durable acceptance; process duplicates safely.
OrderingUse event timestamps and state checks rather than assuming delivery order.
RecoveryRoute failures to retry or dead-letter handling without losing event identity.

Receiver contract

POST /webhooks/pesaguard
  Content-Type: application/json
  X-PesaGuard-Signature: <signature>
  X-PesaGuard-Delivery-Id: delivery_01J...

  { "event": "transaction.matched", "id": "event_01J...", "tenant_id": "tenant_123" }

Header names and event fields are illustrative until the deployment publishes the exact webhook contract. A receiver should fail closed on an invalid signature and retain the raw body needed to verify and audit the attempt.

Signature and secret rotation

  1. Read the new signature scheme and canonicalization rules from the release contract.
  2. Deploy verification for the new secret while the old secret remains accepted for the announced overlap.
  3. Verify against the raw body before JSON parsing.
  4. Record which key version verified the delivery without logging secret material.
  5. Remove the old secret after traffic confirms the overlap is complete.

Replay and duplicate testing

ScenarioExpected consumer behavior
Same delivery twiceOne durable event and one downstream effect.
Out of order eventsState transition checks prevent regression.
Malformed bodyReject safely and retain delivery evidence.
Consumer outageProvider retry or dead-letter path preserves identity.
Signature mismatchReject before parsing or acting on the payload.

Rollback

If rejection or duplicate rates increase, disable the producer change or route traffic to the previous consumer contract while preserving queued events. Do not discard deliveries during rollback; replay them after the receiver is compatible.
