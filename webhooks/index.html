Webhooks

Webhook delivery

Outbound webhooks carry exceptions and notifications to systems you run. Every delivery is signed, retried on failure with bounded backoff, and dead-lettered when exhausted: never silently dropped.

  • Signed by default: consumers verify the sender before trusting the payload.
  • Attempts are recorded: delivery history per event, with outcomes.
  • Exhausted deliveries are retained: dead letters stay visible for investigation and replay.
  • Replay is safe: idempotency applies to delivery exactly as it does to ingestion.

The ops API exposes webhook delivery events (event id, type, source, received and processing times, status, HTTP status, retry count, error and the related transaction) under the integrations scopes: see the API reference and the contract at api-reference/openapi.json.

Receiver contract

Verify the sender, accept durably, process idempotently and expose every attempt for investigation.

Delivery lifecycle

  1. PesaGuard creates an event with a stable event and delivery identity.
  2. The payload is signed and sent to the configured receiver.
  3. The receiver verifies the raw body before parsing.
  4. The receiver persists the event and acknowledges only after durable acceptance.
  5. Failures are retried with bounded backoff, then retained in a dead-letter path.
  6. Operators can inspect and replay the delivery without losing its identity.

Minimum receiver requirements

RequirementWhy
Raw-body signature verificationPrevents a modified payload from being trusted.
Fast acknowledgement after persistencePrevents timeouts while avoiding data loss.
Idempotent event handlingProvider retries must not create duplicate effects.
Unknown-field toleranceAdditive payload changes remain compatible.
Observable delivery identityOperators can trace attempts, retries and replay.
