Retries and dead letters

Transient failures are retried with bounded backoff. When retries are exhausted the delivery moves to the dead-letter path, where it stays visible and replayable: a failed delivery never disappears.

  • Each attempt is recorded with its outcome, so you can answer what was sent and when.
  • Exhausted deliveries are dead-lettered and retained for investigation.
  • Replay from the dead letter is safe: idempotency applies to delivery like everything else.
  • Retry schedules are bounded on purpose; unbounded retries only hide an outage.

The ops API surfaces these delivery events with retry counts and error details under the integrations:read scope.

Retry decision

FailureRetry behaviorReceiver action
Network timeoutRetry with bounded backoff.Keep processing idempotent.
5xx responseRetry and record response status.Investigate dependency or receiver health.
4xx signature failureDo not blindly retry.Fix secret or verification configuration.
Exhausted attemptsMove to dead letter.Inspect, correct and replay deliberately.

Replay procedure

  1. Inspect delivery payload, error, attempt count and tenant context.
  2. Correct receiver, secret or dependency behavior.
  3. Replay using the original event and delivery identity.
  4. Confirm one downstream effect and a successful acknowledgement.
  5. Close the dead-letter record with an operator reason.
